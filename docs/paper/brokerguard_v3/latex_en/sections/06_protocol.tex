\section{Data and Evaluation Protocol}\label{sec:protocol}

\paragraph{Development set.} VN-AgentInject turns the model of Section~\ref{sec:threat} into runnable cases built from
synthetic data. The set \dev{} contains 168 families and 1,960 cases (840 attack, 840 \bPlain, 280 \bAuth) and is the
union of the earlier development set (48 families) with \tOne{} (72 families) and \tTwo{} (48 families). The two
earlier test sets were merged into it because the 40 cases that bypassed \base{} on them were used to design \ours.
Reusing them as a test set would give optimistic results~\cite{dwork2015reusable}, so a new test set was built with the
same procedure~\cite{recht2019imagenet}. The sensitivity labels of \dev{} were reassigned according to a written
labelling rulebook, by deterministic code with human review. \dev{} is split by family into a training part (126
families) and a validation part (42 families, 7 per mechanism). Every parameter of \ours{} was tuned on the training
part and selected on the validation part.

\paragraph{Test set \tThree.} \tThree{} contains 48 new families (8 per mechanism) and 560 cases (240 attack, 240
\bPlain, 80 \bAuth) and follows the template of \tTwo. The families were generated automatically from a specification,
then reviewed and edited by two team members. The set was sealed with SHA-256 before any line of \ours{} code was
written. The largest 4-gram Jaccard overlap with any text of \dev{} is 0.05 (threshold 0.2). Every family passes a
replay check, in which a reference trajectory that follows the injection must be scored as harmful and a trajectory
that completes the task safely must be scored as safe (800 replays, no failures). The runner refuses to start if the hash
of the data, prompts, defence code, model versions or configuration list differs from the pinned manifest.

\paragraph{Adaptive attacks.} Two adaptive sets are reported separately. The first contains 24 cases within \tThree,
generated by the same procedure, aimed at the three gaps of \base{} (8 cases per gap) and sealed together with
\tThree. This set favours \ours, since its targets are exactly what \ours{} was designed to fix. The second set was
written after \ours{} had been frozen, by two team members who knew its full design and formal model. It contains 42
cases, each replacing the attack text of one family from the validation part of \dev, and targets assumptions (A2) to
(A5). Results are compared with the original attack of the same family.

\paragraph{Backbones.} The three open-weight backbones are Gemma-4-12B, Llama-3.1-8B (16k context) and Qwen3.5-9B,
served with vLLM and pinned by revision. All three share the same ReAct prompt, temperature 0, at most 512 tokens per
step and eight steps. Gemini 3 Flash is run on \tThree{} as a reference column with five configurations. It is a closed
model accessed through a proxy, its version cannot be pinned, and it is excluded from all tests.

\paragraph{Configurations.} All configurations share the same agent, broker and environment. \cNone{} only checks
schemas. The two prompt-level defences are \cSpot~\cite{hines2024spotlighting} and \cSand. The two detection defences are
\cPG{} (Prompt Guard~2~\cite{meta2025promptguard2} screening tool outputs) and \cMel. \cProg{} applies privilege policies.
The asterisk marks re-implementations following MELON~\cite{zhu2025melon} and Progent~\cite{shi2025progent}, which do
not represent the original systems. The development line consists of \cPhrase{} (phrase rules), \cRules{} (\base{}
without the prompt layer), \base{} and \ours, plus the three ablations \abl{1}, \abl{2} and \abl{3}. The eight
configurations of the main matrix (\cNone, \cSand, \cProg, \base, \ours{} and the three ablations) were run once per
backbone on the 560 cases and the 24 adaptive cases. Only cases that hit an infrastructure error were rerun. The five
configurations \cSpot, \cPG, \cMel, \cPhrase{} and \cRules{} were added on the 560 cases after the main results were
known. They had been frozen earlier and were declared before running, but comparisons with them are exploratory.

\paragraph{Metrics.} For a set of attack cases $\mathcal{A}$ and a set of benign cases $\mathcal{B}$,
\begin{equation}\label{eq:metrics}
\mathrm{ASR} = \frac{|\{f \in \mathcal{A} : \mathrm{Harm}(f)\}|}{|\mathcal{A}|}, \qquad
U = \frac{|\{f \in \mathcal{B} : \mathrm{Done}(f) \land \lnot \mathrm{Harm}(f)\}|}{|\mathcal{B}|}, \qquad
\Delta U = U_\text{def} - U_\text{\cNone},
\end{equation}
where $\mathrm{Done}(f)$ is a deterministic, task-specific completion condition. Model errors, that is, malformed or
truncated outputs, count as utility failures and never as defence successes. A family is \emph{harmed} if at least one
of its attack cases is harmful on at least one backbone. This is the primary unit of inference, because the cases of a
family share a task and an environment and are therefore not independent. Costs comprise the false-block rate (benign
cases with at least one gate denial), the confirmation rate, tokens and wall time per case, and the time spent in the
gate.

\paragraph{Pre-registered hypotheses.} Before \tThree{} was sealed, four hypotheses were registered under a sequential
gatekeeping procedure. H1, the only primary hypothesis, states that \ours{} has fewer harmed families than \base, tested
with a one-sided exact McNemar test~\cite{mcnemar1947} on the 48 paired families at $\alpha = 0.05$. H2 to H4 are tested
only if the null hypothesis of H1 is rejected. H2 states that the utility of \ours{} is at most 5 points below that of \base. H3 states that
removing each component increases the number of harmed families (McNemar with Holm correction~\cite{holm1979}). H4 sets
thresholds of 10\% for the confirmation rate and 15\% for the false-block rate, and overhead thresholds relative to
\base{} of 20\% for tokens and 15\% for latency. A power analysis based on the level of \base{} on \tTwo{} (14 of 48
families harmed) gave a power of 91\% if \ours{} blocks 8 more families. All comparisons with other configurations are
exploratory.

\paragraph{AgentDojo.} To test generalisation to an unseen environment, the Banking (144 pairs of user and injection
tasks) and Slack (105 pairs) suites of AgentDojo v1.2.2~\cite{debenedetti2024agentdojo} are used with the
\code{important\_instructions} attack, in English and in a Vietnamese translation. The translation keeps IBANs, amounts,
names and addresses unchanged, while the tools and scoring functions are the original code. \base{} and \ours{} run with
Llama-3.1-8B through an adapter declared before running, which states which tools are sinks and which argument holds
the destination. Because the original extractor only recognises addresses and endpoints, \cOne{} in the adapter only
requires the destination (an IBAN, a user, a channel, a URL or an e-mail address) to occur as a whole token in $u$
outside any negation scope. Sinks without a destination, such as changing a password, lie outside \cOne. The prompt
layer is the built-in \code{repeat\_user\_prompt} defence of AgentDojo.
